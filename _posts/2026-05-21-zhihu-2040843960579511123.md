</blockquote><figure data-size="normal"><img src="/assets/blog/images/d6a8fd023bda9f00c2de.png" data-caption="" data-size="normal" data-rawwidth="2364" data-rawheight="742" class="origin_image zh-lightbox-thumb" width="2364" data-original="/assets/blog/images/d6a8fd023bda9f00c2de.png"></figure><p data-pid="GK4EkMIo">过去一年，AI Agent 的讨论越来越热。</p><p data-pid="RdNFZTKf">但你有没有发现一个变化： 大家已经不再满足于“让模型回答问题”，而是在追问一个更硬核的问题——<b>如何让 Agent 稳定地完成复杂任务？</b></p><p data-pid="8tTAKvo0">写代码、查网页、跑终端、调 API、操作 GUI、协作多智能体、长期记住经验……这些任务的共同特点是：<b>不是一步问答，而是一连串动作。</b></p><p data-pid="hS1FZ1sh">也正是在这个背景下，一个关键词开始频繁出现：</p><p data-pid="7a7BwW0X"><b>Skill，智能体技能。</b></p><p data-pid="7WsLjSvu">港科大（广州）与 IDEA Research 等机构最新综述 <i>A Survey of Agent Skills: Toward Procedural Infrastructure for LLM Agents</i>，系统梳理了 Agent Skill 的概念、表示、生命周期、运行时集成、治理风险与应用版图。文章给出的核心判断非常值得关注：</p><p data-pid="SJk2WKnU"><b>Skill 不是简单的 Prompt，也不是普通 Tool，而是 LLM Agent 迈向“可复用行动能力”的关键基础设施。</b></p><p data-pid="1cO3K2rU">这篇文章，我们就用一文讲清楚：Agent Skill 到底是什么？为什么重要？它会如何改变下一代智能体系统？</p><figure data-size="normal"><img src="/assets/blog/images/c4d6bc4fd028564fd2f1.png" data-caption="" data-size="normal" data-rawwidth="1222" data-rawheight="1700" class="origin_image zh-lightbox-thumb" width="1222" data-original="/assets/blog/images/c4d6bc4fd028564fd2f1.png"></figure><h2>01 从 Prompt 到 Skill：Agent 真正缺的不是“更会说”，而是“更会做”</h2><p data-pid="UnzRYIER">早期的大模型应用，主要依赖 Prompt Engineering。</p><p data-pid="F4NSu6XN">后来，大家发现只靠提示词不够，于是有了 Context Engineering：把记忆、检索、工具说明、用户偏好、任务背景都塞进上下文里。</p><p data-pid="PwyxuVx2">再后来，Agent 开始进入真实环境：文件系统、浏览器、终端、数据库、API、代码仓库、多人协作流程……</p><p data-pid="fLJK3xu6">这时问题变了。</p><p data-pid="UAHtc0WS">不是“怎么问模型”，而是：</p><p data-pid="fv04CLyG"><b>如何让模型在复杂环境里稳定行动？</b></p><p data-pid="vQtml8vk">综述中提到，Agent 工程正在经历一条清晰路径：</p><p data-pid="ZcjbeQKb"><b>Prompt Engineering → Context Engineering → Harness Engineering</b></p><p data-pid="BJZ10MCl">所谓 Harness，可以理解为包裹在模型外部的执行外壳：它负责连接文件、工具、终端、浏览器、记忆、权限和人类反馈。</p><p data-pid="FJf1q-H6">而 Skill，正是在这个外壳里逐渐浮现出来的新抽象。</p><figure data-size="normal"><img src="/assets/blog/images/86fe1f9283e3f9fa2b4a.png" data-caption="" data-size="normal" data-rawwidth="924" data-rawheight="395" class="origin_image zh-lightbox-thumb" width="924" data-original="/assets/blog/images/86fe1f9283e3f9fa2b4a.png"></figure><p data-pid="lKIPwk5E">为什么需要 Skill？</p><p data-pid="dUwOroYM">因为 Agent 不能每次都从零开始推理。</p><p data-pid="r1OdIYw8">一个人学会调试代码后，不会每次都重新发明调试流程；一个工程师熟悉某个项目后，也不会每次都重新探索目录结构。人类会把经验压缩成套路、方法、流程和检查清单。</p><p data-pid="nuVEMQqJ">Agent 也一样。</p><p data-pid="Q_O50mPV"><b>Skill 的本质，就是把反复成功的经验，压缩成未来可复用的行动程序。</b></p><hr><h2>02 一句话定义 Agent Skill</h2><p data-pid="UzE5dPW6">综述给出了一个非常清晰的定义：</p><p data-pid="OgORBFgu"><b>Agent Skill 是一种可复用的程序性知识单元，它将重复经验、人类专家知识，或二者结合，压缩成可执行、可迁移、可验证的行为模式。</b></p><p data-pid="E9qK32Jz">换句话说，Skill 解决的是“知道怎么做”的问题。</p><p data-pid="uk_QtYfX">它通常需要回答四件事：</p><ol>
<li data-pid="2cTjBg1i">
<b>什么时候用？</b> 适用条件是什么？面对什么任务、输入、环境状态时应该触发？</li>
<li data-pid="x1-RhWvV">
<b>怎么做？</b> 具体步骤是什么？是自然语言流程、代码片段、决策图，还是文件夹式 Skill 包？</li>
<li data-pid="Q57cYidk">
<b>用什么资源？</b> 需要哪些工具、脚本、文件、API、记忆或外部资料？</li>
<li data-pid="qmtBDyZo">
<b>怎么判断做成了？</b> 有什么完成条件、质量检查、错误信号或验证标准？</li>
</ol><p data-pid="eKr38wVG">综述中将 Skill 形式化为：</p><div class="highlight"><pre><code class="language-text"><span></span>s = &lt;C, P, R, E&gt;
</code></pre></div><p data-pid="FnA_by6b">其中：</p><ul>
<li data-pid="JfpcQsCF">
<code>C</code>：适用条件 Condition</li>
<li data-pid="RwS3hASK">
<code>P</code>：程序核心 Procedure</li>
<li data-pid="hCFir6I7">
<code>R</code>：资源接口 Resource</li>
<li data-pid="hbygU-Rh">
<code>E</code>：评估标准 Evaluation</li>
</ul><p data-pid="zqL7LejV">这个定义很关键，因为它把 Skill 从“提示词片段”升级成了一个完整的行动单元。</p><p data-pid="QHGIhzVB"><b>一个好的 Skill，不只是告诉 Agent 要做什么，还告诉它什么时候做、怎么做、依赖什么、如何验收。</b></p><hr><h2>03 Skill 位于 Memory 和 Rule 之间：它是“知道”到“做到”的桥梁</h2><p data-pid="eUz2_3f_">很多人会问：Skill 和 Memory 有什么区别？和 Rule 又有什么区别？</p><p data-pid="tkpE26O6">可以这样理解：</p><ul>
<li data-pid="WyT_oAhH">
<b>Memory</b>：记住过去发生了什么</li>
<li data-pid="-2n7of7R">
<b>Rule</b>：抽象出一般原则</li>
<li data-pid="weenljTU">
<b>Skill</b>：把经验变成可执行流程</li>
</ul><p data-pid="_k_pnLr_">比如，一个 Agent 做过一次网页购物任务。</p><p data-pid="yraTy79m">Memory 会保存：“我上次在某网站搜索了 laptop，筛选了价格，加入购物车。”</p><p data-pid="SiMGotvT">Rule 可能会总结：“购物前要确认商品是否符合需求。”</p><p data-pid="2Z6CEW6J">Skill 则会写成：“当任务要求购买商品时，先解析约束条件，再搜索关键词，筛选候选商品，逐项检查颜色、尺寸、价格、库存，最后加入购物车并确认订单状态。”</p><p data-pid="ajKku88K">这就是区别。</p><p data-pid="d_3pGXh8"><b>Memory 记录事实，Rule 提炼原则，Skill 组织行动。</b></p><figure data-size="normal"><img src="/assets/blog/images/55b93fb3b53a643d3d85.png" data-caption="" data-size="normal" data-rawwidth="740" data-rawheight="432" class="origin_image zh-lightbox-thumb" width="740" data-original="/assets/blog/images/55b93fb3b53a643d3d85.png"></figure><p data-pid="UeVUGhyS">综述中特别强调，Skill 的价值不只是节省存储空间，更在于：</p><p data-pid="rWLapCXc"><b>减少重复规划、稳定长任务执行、提高行为可解释性。</b></p><p data-pid="IPK0cyFX">对长程任务而言，这一点非常重要。因为 Agent 最大的问题往往不是“不知道答案”，而是在多步执行中：</p><ul>
<li data-pid="tzO15xMd">走偏；</li>
<li data-pid="mdBMWz84">忘记目标；</li>
<li data-pid="oX5apWaq">重复探索；</li>
<li data-pid="k6nUZjDn">错误调用工具；</li>
<li data-pid="Eto-uQro">没有检查结果；</li>
<li data-pid="ubapxpa-">无法复用过去经验。</li>
</ul><p data-pid="Hh12UqRM">Skill 的作用，就是把过去摸索出来的路径沉淀下来，下次直接复用。</p><hr><h2>04 Agent Skill 可以长什么样？</h2><p data-pid="LKJaBtAW">综述将 Agent Skill 的表示方式分成几类。每一种都对应不同的使用场景。</p><h3>1. 自然语言 Skill：最轻量，也最灵活</h3><p data-pid="ThQ8rwIG">最简单的 Skill，就是一段自然语言经验总结。</p><p data-pid="yg8yRX1U">例如：</p><blockquote data-pid="RWSTdWBw"> 在网页搜索任务中，如果第一次查询没有得到结果，不要重复同一个搜索词；应该拆分问题、替换关键词，或先查询实体背景信息。</blockquote><p data-pid="ThnHUZ22">这种形式很像经验卡片、SOP、任务提示或启发式规则。</p><p data-pid="5_wCGbRp">优点是：</p><p data-pid="5ZXo4rd6"><b>易写、易读、易迁移。</b></p><p data-pid="aaNylqoZ">缺点也明显：</p><p data-pid="ccXiE1uP"><b>执行依赖模型理解，不保证流程稳定。</b></p><p data-pid="xBwzjO9P">适合用于搜索、问答、网页浏览、客服、轻量办公等场景。</p><hr><h3>2. 代码片段 Skill：把经验变成可运行程序</h3><p data-pid="ZI-gNjpz">有些 Skill 可以直接写成函数。</p><p data-pid="L1sK5EUg">比如在 Minecraft 智能体 Voyager 中，Agent 可以把“砍树”“制作石镐”“与僵尸战斗”等行为封装成可复用代码。</p><p data-pid="VcJ1WGl9">这类 Skill 通常包含：</p><ul>
<li data-pid="n0zwMucY">自然语言描述；</li>
<li data-pid="YjK0htkr">可执行程序；</li>
<li data-pid="ypNpofav">参数说明；</li>
<li data-pid="jElibSpA">调用条件。</li>
</ul><p data-pid="nt40m2zW">优点是：</p><p data-pid="NN3r7qRi"><b>可执行、可组合、结果更稳定。</b></p><p data-pid="6_uAtCiW">缺点是：</p><p data-pid="Kmw7IaCf"><b>需要运行环境，也需要测试代码正确性。</b></p><p data-pid="4jhmsevG">在软件工程、数据处理、终端任务、机器人控制中，代码 Skill 非常重要。</p><hr><h3>3. 决策图 Skill：把流程写成可检查的工作流</h3><p data-pid="LyA9Z10P">有些任务不是线性步骤，而是包含分支、判断和循环。</p><p data-pid="QUAZt-dg">比如售后处理、表单审核、网页任务、客服 SOP。</p><p data-pid="XAInmM-5">这时可以用决策图表示 Skill：</p><ul>
<li data-pid="FPrcdb5z">节点表示动作；</li>
<li data-pid="7PnPXKlw">边表示条件；</li>
<li data-pid="jp5D2hEW">分支表示不同情况；</li>
<li data-pid="_DT4bEiE">路径表示执行流程。</li>
</ul><p data-pid="X8GVhPcE">这种方式的优势在于：</p><p data-pid="wcsGc-w2"><b>可检查、可编辑、可控性强。</b></p><p data-pid="FgN1pavh">它比自然语言更结构化，又比代码更容易让非程序员理解。</p><hr><h3>4. 文件系统式 Skill：Claude Skills 代表的新范式</h3><p data-pid="WjOLOzDy">综述中重点讨论了 Anthropic Claude Skills 的文件夹式设计。</p><p data-pid="rw4nK7vL">一个 Skill 可以是一个目录：</p><div class="highlight"><pre><code class="language-text"><span></span>PDF-SKILL/
├── SKILL.md
├── FORMS.md
├── REFERENCE.md
└── scripts/
    ├── extract_tables.py
    ├── fill_forms.py
    └── validate_pdf.py
</code></pre></div><p data-pid="HqPdRm0j">其中 <code>SKILL.md</code> 是核心文件，里面包含：</p><ul>
<li data-pid="_XIy59aO">Skill 名称；</li>
<li data-pid="bAXGBd_o">描述；</li>
<li data-pid="gOCCnFYP">触发条件；</li>
<li data-pid="9F3vLe6h">使用说明；</li>
<li data-pid="cx-pEx8U">示例；</li>
<li data-pid="p7k2yaL9">资源链接；</li>
<li data-pid="iWYLJZBc">可调用脚本。</li>
</ul><p data-pid="JwRtBA16">这个设计有一个非常重要的思想：</p><p data-pid="w38efkC2"><b>渐进式披露。</b></p><p data-pid="JLTXmA4Z">也就是说，Agent 一开始只看到 Skill 的名称和描述。只有当任务匹配时，才加载完整 <code>SKILL.md</code>；只有真正需要时，才继续读取脚本、参考文档或模板。</p><p data-pid="QQA8seg5">这解决了一个关键矛盾：</p><p data-pid="unHhQItc"><b>Skill 越详细越有用，但上下文窗口越容易爆。</b></p><p data-pid="5jT2b9Q8">文件夹式 Skill 让知识可以放在外部，按需加载，而不是一次性塞进 Prompt。</p><figure data-size="normal"><img src="/assets/blog/images/49daa9f460a29c4e0a4c.png" data-caption="" data-size="normal" data-rawwidth="1161" data-rawheight="487" class="origin_image zh-lightbox-thumb" width="1161" data-original="/assets/blog/images/49daa9f460a29c4e0a4c.png"></figure><hr><h2>05 Skill 的生命周期：不是写完就完，而是要持续进化</h2><p data-pid="Xww4ZkOg">综述提出，Skill 不应被看作静态提示词，而是一种会经历完整生命周期的操作性知识。</p><p data-pid="thhKHLmv">它包括五个阶段：</p><div class="highlight"><pre><code class="language-text"><span></span>获取 → 存储 → 使用 → 维护 → 内化
</code></pre></div><h3>获取：从经验中提炼 Skill</h3><p data-pid="jQhHJO0L">Agent 可以从三类来源获取 Skill：</p><p data-pid="9Jnkw9vU">第一类是成功轨迹。 比如一次任务做对了，就从中提炼可复用流程。</p><p data-pid="vyImvlgr">第二类是失败对比。 成功经验重要，失败经验同样重要。因为失败能告诉 Agent：哪些条件不满足、哪些步骤容易错、什么时候需要回退。</p><p data-pid="tYfRyRaf">第三类是主动探索。 Agent 可以主动尝试新任务、阅读文档、分析代码库，从外部资源中挖掘新的 Skill。</p><p data-pid="NenpznSa">这里最难的是把握抽象粒度。</p><p data-pid="-HnNhYMN"><b>Skill 太具体，就变成一次任务记录；Skill 太抽象，又无法执行。</b></p><p data-pid="r6svOQku">好的 Skill 应该像工程师写的操作手册：既不是流水账，也不是空话。</p><hr><h3>存储：Skill 库不能只是一个大文件夹</h3><p data-pid="u3o3YRWg">当 Skill 数量变多后，问题会立刻出现：</p><ul>
<li data-pid="Awim5s1m">怎么找到正确 Skill？</li>
<li data-pid="s0Z769Hr">哪些 Skill 是高层规划，哪些是低层操作？</li>
<li data-pid="u6Vfo7xs">Skill 之间有没有依赖关系？</li>
<li data-pid="dmNPmFs8">哪些 Skill 可以组合？</li>
<li data-pid="8trdPhVs">哪些已经过期？</li>
</ul><p data-pid="kILJXIj_">综述总结了几种 Skill 存储方式：</p><ul>
<li data-pid="c3Fh5OY5">
<b>扁平存储</b>：简单，但很快混乱；</li>
<li data-pid="vDe3m11s">
<b>层级存储</b>：按粒度组织，如规划 Skill、功能 Skill、原子 Skill；</li>
<li data-pid="bIO-tkBM">
<b>树状存储</b>：按能力领域导航；</li>
<li data-pid="W10oWqJK">
<b>图结构存储</b>：表达依赖、组合、替代、相似关系。</li>
</ul><p data-pid="BitELp_t">未来大规模 Skill 系统很可能不是一个“技能列表”，而是一个 <b>Skill Graph</b>。</p><figure data-size="normal"><img src="/assets/blog/images/d707c6db36c0aef20a3c.png" data-caption="" data-size="normal" data-rawwidth="1177" data-rawheight="583" class="origin_image zh-lightbox-thumb" width="1177" data-original="/assets/blog/images/d707c6db36c0aef20a3c.png"></figure><hr><h3>使用：不是检索一个 Skill，而是装配一组可执行能力</h3><p data-pid="9x-EpLBH">很多人会把 Skill Retrieval 理解成语义搜索：用户任务来了，找最相似的 Skill。</p><p data-pid="_yXSNMbI">但综述指出，这还远远不够。</p><p data-pid="CG1CQKzd">真正的 Skill 使用，需要同时考虑：</p><ul>
<li data-pid="j3itZ4hA">当前任务意图；</li>
<li data-pid="I6nJd8ns">环境状态；</li>
<li data-pid="28ikhIeh">执行历史；</li>
<li data-pid="HCzquurW">上下文预算；</li>
<li data-pid="QzmxrdEO">Skill 之间的依赖；</li>
<li data-pid="Fccs-wyK">工具可用性；</li>
<li data-pid="_2sbzeCf">风险等级。</li>
</ul><p data-pid="IH36MKD4">比如一个“生成月度财务报告”的 Skill，可能还依赖：</p><ul>
<li data-pid="Ymrz2qpO">读取 Excel 的 Skill；</li>
<li data-pid="fblFbv7M">清洗数据的 Skill；</li>
<li data-pid="C0KFFKTu">调用图表工具的 Skill；</li>
<li data-pid="To29t90k">检查数值一致性的 Skill；</li>
<li data-pid="iF3Hbe2E">输出 PDF 的 Skill。</li>
</ul><p data-pid="V_5etEPG">所以，Skill 使用不是简单“命中一个文档”，而是：</p><p data-pid="NwCrRhZM"><b>在有限上下文中，组装一组最小但完整的执行能力。</b></p><hr><h3>维护：Skill 会变旧，也会互相冲突</h3><p data-pid="MiAGckdK">Skill 写出来后，不代表永远正确。</p><p data-pid="hydMpds-">工具 API 会变，网站页面会变，项目规范会变，安全策略会变。</p><p data-pid="gUd3apCD">因此 Skill 需要维护：</p><ul>
<li data-pid="NrZo-uOE">失败后修复；</li>
<li data-pid="8VlN3TPG">成功后强化；</li>
<li data-pid="4eFn4PxO">冗余 Skill 合并；</li>
<li data-pid="rmqpY2fw">低价值 Skill 下线；</li>
<li data-pid="yrvBLRLP">过期 Skill 标记；</li>
<li data-pid="kMU-rlOp">版本回滚；</li>
<li data-pid="7_kuVu5s">测试验证。</li>
</ul><p data-pid="gaMIkwvq">这很像软件工程中的包管理和版本治理。</p><p data-pid="WQjOuyeI"><b>Skill 越像基础设施，就越需要工程化维护。</b></p><hr><h3>内化：成熟 Skill 最终可能进入模型本身</h3><p data-pid="l7v-_Z55">外部 Skill 有好处：模块化、可编辑、可审计。</p><p data-pid="p5bs2PUS">但也有成本：检索噪声、上下文占用、调用延迟。</p><p data-pid="SqjcrNbF">因此，综述提出一个有意思的方向：当某些 Skill 足够稳定、通用、频繁使用时，可以通过训练或蒸馏，把它们“内化”进模型行为中。</p><p data-pid="UNJ9Zw1u">也就是说：</p><p data-pid="nSDWMbMR"><b>Skill 库既是执行工具，也是训练脚手架。</b></p><p data-pid="7S-Pa5bg">短期靠外部 Skill 提升能力，长期把成熟经验压缩进模型参数。</p><hr><h2>06 Runtime Integration：Skill 真正发挥作用的地方</h2><p data-pid="Pg7y0BzD">Skill 不是摆在仓库里的说明书。它必须进入运行时，才能变成行动。</p><p data-pid="msXJPgCO">综述把运行时集成分成几类。</p><h3>终端 Agent：Skill 是命令行世界里的安全绳</h3><p data-pid="_hG4OrZ6">终端非常强大，也非常危险。</p><p data-pid="suP-LF7I">Agent 可以在终端里：</p><ul>
<li data-pid="JXFkFeMB">查看文件；</li>
<li data-pid="bitLJ0VI">安装依赖；</li>
<li data-pid="jI9LUX5P">跑测试；</li>
<li data-pid="IZPxDegh">修改代码；</li>
<li data-pid="8NoNzVnM">调用脚本；</li>
<li data-pid="zF5iutWA">访问服务；</li>
<li data-pid="kSnT5MZZ">生成报告。</li>
</ul><p data-pid="Yg5_ze2L">但终端动作空间极其开放，Agent 很容易乱试命令。</p><p data-pid="n8IFwATl">Skill 在这里的作用是：</p><p data-pid="J6qBa5rs"><b>把反复出现的命令模式、诊断流程、验证步骤、人工确认点封装起来。</b></p><p data-pid="nl6P9Pws">比如一个“修复 Python 项目测试失败”的 Skill，可以规定：</p><ol>
<li data-pid="2y8DDF7I">先运行测试并保存日志；</li>
<li data-pid="u2FSiAth">定位失败文件；</li>
<li data-pid="LnJwkMRZ">阅读相关函数；</li>
<li data-pid="3Hkq8e4P">做最小修改；</li>
<li data-pid="ndsY4PO1">重新跑目标测试；</li>
<li data-pid="8N_GbG1N">再跑全量测试；</li>
<li data-pid="wBYzQA0L">总结变更。</li>
</ol><p data-pid="TWwlX-r8">这比让 Agent 每次自由发挥可靠得多。</p><hr><h3>Tool Agent：Skill 是高层意图和底层 API 的适配器</h3><p data-pid="2nlMYQtI">Tool 很重要，但 Tool 本身只告诉模型“能调用什么”。</p><p data-pid="X-T5FVB6">它通常不会告诉模型：</p><ul>
<li data-pid="VKq86l_Z">什么时候调用；</li>
<li data-pid="fi6slHJ7">多个工具如何排序；</li>
<li data-pid="I4lUlklK">中间结果如何判断；</li>
<li data-pid="ILgt6NPi">失败如何恢复；</li>
<li data-pid="_5YwYoWW">什么时候停止。</li>
</ul><p data-pid="9GltzlFW">Skill 正好填补这个空白。</p><p data-pid="WuStyjjn"><b>Tool 是原子动作，Skill 是可复用流程。</b></p><p data-pid="ZUGHnz_5">比如电商场景中，Tool 可能包括：</p><ul>
<li data-pid="_kpD49vt">搜索商品；</li>
<li data-pid="c2_M-5E-">查看商品详情；</li>
<li data-pid="jlApru4I">加入购物车；</li>
<li data-pid="ggGC6RBy">结算；</li>
<li data-pid="lCQzNK8m">查询订单状态。</li>
</ul><p data-pid="qjxZD5m-">而购买商品的 Skill 会组织这些 Tool：</p><div class="highlight"><pre><code class="language-text"><span></span>解析需求 → 搜索商品 → 筛选候选 → 检查属性 → 加入购物车 → 确认订单
</code></pre></div><p data-pid="RZmxm0XJ">这就是为什么综述强调：</p><p data-pid="p91lz1TD"><b>Skill 既不是 Prompt，也不是 Tool，而是连接推理与执行的中间层。</b></p><figure data-size="normal"><img src="/assets/blog/images/1ca5ce7697ae28baf91f.png" data-caption="" data-size="normal" data-rawwidth="1469" data-rawheight="986" class="origin_image zh-lightbox-thumb" width="1469" data-original="/assets/blog/images/1ca5ce7697ae28baf91f.png"></figure><hr><h3>多智能体系统：Skill 是协作协议</h3><p data-pid="cF4GUACO">在多 Agent 系统里，不同 Agent 可能扮演产品经理、工程师、测试员、审查员等角色。</p><p data-pid="aFcv9Rtb">但如果没有 Skill，协作很容易变成开放式聊天：</p><ul>
<li data-pid="wSTm9zrd">谁负责什么？</li>
<li data-pid="zb5E_Hvh">输出格式是什么？</li>
<li data-pid="YtGzk0YO">什么时候交接？</li>
<li data-pid="jgZqA7Bb">失败如何反馈？</li>
<li data-pid="DJdf-3Kk">谁来验证？</li>
</ul><p data-pid="GR9ox-qC">Skill 可以把这些协作模式写成流程：</p><p data-pid="s25Vq9Ce"><b>角色职责、输入输出、交接标准、验证方式、异常处理。</b></p><p data-pid="CXBCPNTQ">从这个角度看，Skill 不只是单个 Agent 的能力，也可以是多智能体系统的“组织记忆”。</p><hr><h3>Agent Harness：未来的运行时会内置 Skill 层</h3><p data-pid="GUBiVmBt">真正成熟的 Agent Harness，不能只是把模型接上工具。</p><p data-pid="Ku0TSUPq">它应该内置 Skill-aware Runtime：</p><ul>
<li data-pid="i6l4oQfy">能根据任务检索 Skill；</li>
<li data-pid="U_5uqZUu">能按需加载 Skill 内容；</li>
<li data-pid="OmvRLNPU">能绑定工具、文件、终端和工作区状态；</li>
<li data-pid="nl0Bni0I">能监控 Skill 是否按预期执行；</li>
<li data-pid="Bt3LaEMC">能记录成功和失败；</li>
<li data-pid="jWozAx3T">能把新经验反哺 Skill 库；</li>
<li data-pid="-QInegHa">能在高风险动作前请求人类确认。</li>
</ul><p data-pid="SBxFrEzx">一句话：</p><p data-pid="dq7ZAYah"><b>未来的 Agent Harness，不只是执行壳，而是 Skill 的运行、治理和进化平台。</b></p><hr><h2>07 Governance：Skill 也会成为新的安全攻击面</h2><p data-pid="eGR-Px4n">Skill 越强大，风险也越大。</p><p data-pid="xRUsb-Mo">因为 Skill 往往可以接触：</p><ul>
<li data-pid="FQAxfNpM">本地文件；</li>
<li data-pid="gfWAHJ_8">API Key；</li>
<li data-pid="yug0Xzgv">终端命令；</li>
<li data-pid="sTgAje49">浏览器状态；</li>
<li data-pid="_S2MJeeW">用户数据；</li>
<li data-pid="xoD-EtZi">外部服务；</li>
<li data-pid="gjJHVt_i">第三方依赖。</li>
</ul><p data-pid="5r2Mz02j">这意味着，Skill 生态很可能继承软件供应链的风险，并引入 Agent 特有的新风险。</p><p data-pid="fMIQc9mw">综述重点讨论了几类威胁：</p><h3>1. Skill 注入攻击</h3><p data-pid="UzoXHiIM">恶意指令可以藏在 Skill 文件、注释、说明文档甚至辅助资源里。</p><p data-pid="1bCWVrak">一旦 Agent 加载 Skill，就可能被诱导执行危险操作。</p><p data-pid="MgnaTven">这比普通 Prompt Injection 更麻烦，因为它不是一次性输入，而是<b>持久化在可复用组件中</b>。</p><hr><h3>2. 恶意 Skill 和后门 Skill</h3><p data-pid="_QU-eVe7">某些 Skill 可能表面上是生产力工具，实际包含：</p><ul>
<li data-pid="ev5XHMOc">凭证窃取；</li>
<li data-pid="QEQsXTIv">数据外传；</li>
<li data-pid="51mbCRBW">远程命令执行；</li>
<li data-pid="CpW2HaWI">隐藏依赖；</li>
<li data-pid="Y7MA-4HN">触发式后门。</li>
</ul><p data-pid="A-bCVkRQ">当 Skill 市场发展起来后，这类风险会类似 npm、PyPI 的供应链问题。</p><hr><h3>3. Skill 克隆与漏洞传播</h3><p data-pid="2SAJPCL6">如果一个有漏洞的 Skill 被大量复制、改名、分发，漏洞也会随之扩散。</p><p data-pid="xFQZVuOE">这会让治理变得很难：你修复了原版，不代表所有衍生版本都安全。</p><hr><h3>4. 权限过大与隐式信任</h3><p data-pid="cE3FX8kZ">用户通常不会逐行审计 Skill。</p><p data-pid="dw_ry3LM">他们可能只看名称、描述、下载量、分类标签。</p><p data-pid="Tb2B-oeg">这会形成“隐式信任”。</p><p data-pid="DL9eFufS">而 Agent 一旦加载 Skill，就可能在用户不完全知情的情况下执行复杂操作。</p><p data-pid="9Gv5fQ79">所以综述提出，未来 Skill 系统必须具备：</p><ul>
<li data-pid="K1aX4H9U">来源验证；</li>
<li data-pid="XOMh7jdV">权限分级；</li>
<li data-pid="4Kr2AomZ">沙箱隔离；</li>
<li data-pid="IyR8ik7S">运行时监控；</li>
<li data-pid="TwSPpEL1">人类审批；</li>
<li data-pid="5bPJ3bFn">安全扫描；</li>
<li data-pid="oujwjTSL">版本审计；</li>
<li data-pid="27MyW9Qd">回滚机制；</li>
<li data-pid="1TMShPmu">合约式约束。</li>
</ul><p data-pid="kJPcxMea"><b>Skill 不是普通文本，而是可执行行为的载体。</b></p><p data-pid="dNrAuPWn">这句话，可能会成为未来 Agent 安全治理的基本共识。</p><hr><h2>08 Skill 的应用版图：从机器人到代码智能体</h2><p data-pid="9ijpffQU">综述最后梳理了 Agent Skill 的主要应用场景。</p><h3>1. 机器人：Skill 是语言和物理动作之间的契约</h3><p data-pid="7_A4YAZ8">在机器人场景中，Skill 可以连接高层语言指令和低层控制器。</p><p data-pid="BRQinygZ">比如“拿起杯子”不是一句话那么简单，它涉及：</p><ul>
<li data-pid="nK33P3Q0">识别杯子；</li>
<li data-pid="27h8dHjq">判断可达性；</li>
<li data-pid="RnAQ-9zd">规划抓取点；</li>
<li data-pid="iMAt0712">控制机械臂；</li>
<li data-pid="wYk8Mo4z">检查是否成功。</li>
</ul><p data-pid="NuKZOT6i">Skill 可以把这些流程封装成可调用能力。</p><hr><h3>2. 开放世界游戏：Skill 是长期探索的积累</h3><p data-pid="Bi__NGGC">Minecraft 等开放世界环境，是研究 Agent Skill 的经典场景。</p><p data-pid="aBDsuTXp">因为这里有长程目标、稀疏奖励、资源依赖、组合任务。</p><p data-pid="BVhJRCZ5">一个 Agent 学会“砍树”“挖石头”“制作工具”后，这些 Skill 可以继续组合成更复杂目标。</p><p data-pid="BMYF1FLW"><b>开放世界游戏展示了 Skill 的一个核心价值：让 Agent 的能力可以持续积累。</b></p><hr><h3>3. Web Agent：Skill 是网页自动化的稳定流程</h3><p data-pid="gAho7iRG">网页任务有很多重复结构：</p><ul>
<li data-pid="517YtUmy">搜索；</li>
<li data-pid="vgteVjnT">筛选；</li>
<li data-pid="a0Xf0LVN">点击；</li>
<li data-pid="I9XFECaZ">填表；</li>
<li data-pid="_aEVBdP5">对比；</li>
<li data-pid="99CuBHN-">提交；</li>
<li data-pid="aTO_TLd_">验证；</li>
<li data-pid="x2zIO5u8">异常恢复。</li>
</ul><p data-pid="KKxZnBiU">Skill 可以把低层点击轨迹抽象成可复用流程，让 Agent 不必每次从头摸索网页。</p><hr><h3>4. GUI / Mobile / OS Agent：Skill 是数字设备操作层</h3><p data-pid="c9Ey6iy4">在手机和桌面系统里，Agent 面对的是像素、窗口、按钮、菜单、弹窗、权限和应用状态。</p><p data-pid="sDVZdpoz">Skill 可以把常见操作编译成参数化模板：</p><ul>
<li data-pid="cOuP3zCC">打开某 App；</li>
<li data-pid="4B9QKlMS">搜索联系人；</li>
<li data-pid="1d-8HYPE">发送消息；</li>
<li data-pid="j7inWeu6">导出文件；</li>
<li data-pid="pef5Xz_u">修改设置；</li>
<li data-pid="n9ay9iuo">跨 App 完成任务。</li>
</ul><p data-pid="mMTmqelw">这类 Skill 的难点是环境会变：App 更新、按钮位置变化、权限弹窗出现、屏幕尺寸不同。</p><p data-pid="wyKNjHW8">因此 GUI Skill 不仅要能执行，还要能检测失败并修复。</p><hr><h3>5. 软件工程 Agent：Skill 是工程实践的抽象</h3><p data-pid="EQEywWIz">在代码智能体中，Skill 尤其重要。</p><p data-pid="OBSvOMfO">真实软件开发不是“写一个函数”这么简单，而是：</p><ul>
<li data-pid="JJSCUwOM">理解 issue；</li>
<li data-pid="V1aBaxqJ">定位文件；</li>
<li data-pid="EimLAVP8">阅读上下文；</li>
<li data-pid="wdtAXGLK">修改代码；</li>
<li data-pid="Nk7T6COM">补测试；</li>
<li data-pid="JLezo_89">跑测试；</li>
<li data-pid="u8WTo4Mb">修复失败；</li>
<li data-pid="gH7B4p84">提交补丁；</li>
<li data-pid="-u-_lY7m">解释变更。</li>
</ul><p data-pid="utXknrsW">这些都是可复用的工程 Skill。</p><p data-pid="tyqLhqID">比如：</p><ul>
<li data-pid="iA-l5B9x">代码定位 Skill；</li>
<li data-pid="1-N9u_55">单元测试生成 Skill；</li>
<li data-pid="R5czoqSE">回归测试 Skill；</li>
<li data-pid="fc0tFmx5">性能优化 Skill；</li>
<li data-pid="_KNb_mOc">依赖升级 Skill；</li>
<li data-pid="fwzAvOuP">Bug 修复 Skill；</li>
<li data-pid="F5YK6Uob">Code Review Skill。</li>
</ul><p data-pid="QA5Ep60w">综述也指出，并不是 Skill 越多越好。错误的 Skill 可能占用上下文、误导模型，甚至降低任务成功率。</p><p data-pid="yzSNYwHU">因此软件工程场景需要的不是“堆 Skill”，而是：</p><p data-pid="jq9rbM_j"><b>可评估、可裁剪、可组合、可验证的 Skill 体系。</b></p><hr><h2>09 未来挑战：Skill 会成为 Agent 的“包管理系统”吗？</h2><p data-pid="3S_KfYjb">综述最后提出了几个非常关键的开放问题。</p><h3>第一，如何评估 Skill 的真实价值？</h3><p data-pid="OSuXfbRc">不能只看任务成功率。</p><p data-pid="DeX1AvEL">还要看：</p><ul>
<li data-pid="qsd96In8">是否被正确触发；</li>
<li data-pid="7jXeWTZA">是否真的改善执行；</li>
<li data-pid="CkgCeg1w">是否减少成本；</li>
<li data-pid="uGjmyjCj">是否能迁移；</li>
<li data-pid="PSlVQX8K">是否鲁棒；</li>
<li data-pid="_vOee-5o">是否和其他 Skill 冲突；</li>
<li data-pid="44SszNbQ">是否带来安全风险。</li>
</ul><p data-pid="0tnXQN1l"><b>Skill 需要作为一等对象被评估，而不是藏在 Agent Pipeline 里的黑盒组件。</b></p><hr><h3>第二，如何处理 Skill 与上下文窗口的矛盾？</h3><p data-pid="BRUGdX5c">Skill 太短，不够用。 Skill 太长，占上下文。 Skill 太多，检索噪声大。 Skill 太少，覆盖不足。</p><p data-pid="zVwwIJhx">未来系统需要更聪明的 Skill Disclosure：</p><p data-pid="pQvQT5OW"><b>在正确时刻，以正确粒度，加载正确内容。</b></p><hr><h3>第三，如何解决 Skill 冲突？</h3><p data-pid="wUQw1HQM">不同 Skill 可能给出相反建议。</p><p data-pid="a-4bcUDu">一个强调安全检查，一个强调速度；一个适用于 React 项目，一个适用于 Vue 项目；一个来自企业内部规范，一个来自开源社区。</p><p data-pid="JYO3IM4Y">这就需要 Skill Arbitration，也就是 Skill 仲裁层。</p><p data-pid="xy7WLkPq">它不仅判断“相关不相关”，还要判断：</p><p data-pid="9iaOv2PS"><b>能不能同时用？谁优先？是否符合当前项目和用户意图？</b></p><hr><h3>第四，如何避免 Skill 漂移？</h3><p data-pid="6eTozFqC">Skill 会在使用中不断修改。</p><p data-pid="_i-yfXlY">但改着改着，可能越来越偏离原本目标。</p><p data-pid="uPiO3nLz">这类似软件中的技术债：</p><ul>
<li data-pid="K-PorRRY">局部补丁越来越多；</li>
<li data-pid="6nE0rdr4">适用边界越来越模糊；</li>
<li data-pid="pn3qharO">行为越来越不可预测；</li>
<li data-pid="wDKEXi__">老版本难以追踪。</li>
</ul><p data-pid="1U9J1MDz">因此 Skill 也需要像软件一样管理：</p><p data-pid="93ri7R0B"><b>版本、测试、回滚、审查、发布、弃用。</b></p><hr><h3>第五，Skill 会不会成为下一代 Agent 基础设施？</h3><p data-pid="tAvl3bgb">这是综述最重要的观点之一。</p><p data-pid="dt-2eGdH">未来 Skill 可能不再是某个 Agent 的小插件，而会像软件包一样，拥有完整生态：</p><ul>
<li data-pid="icxUOQKz">Skill Registry；</li>
<li data-pid="gl7EXGsx">Skill Package Manager；</li>
<li data-pid="L0kblpT5">依赖管理；</li>
<li data-pid="QV1d2Cq_">权限模型；</li>
<li data-pid="qj1BX1UN">安全扫描；</li>
<li data-pid="tB_t4Zm0">版本控制；</li>
<li data-pid="iLJtbPCK">评价体系；</li>
<li data-pid="D863jPQU">运行时隔离；</li>
<li data-pid="oZ0P6_2l">企业私有 Skill 库。</li>
</ul><p data-pid="o-UuRvZJ">也就是说：</p><p data-pid="uMgBJWGr"><b>Agent Skill 很可能成为 AI Agent 时代的“npm / PyPI”。</b></p><p data-pid="NV9-_yUS">但这一次，包里装的不只是代码，还有 Agent 的行为模式。</p><hr><h2>10 总结：Skill 是 Agent 从“聪明”走向“可靠”的关键一步</h2><p data-pid="c9yPYzmS">这篇综述最大的价值，是把 Agent Skill 从零散概念整理成了一个完整框架：</p><ul>
<li data-pid="AdZSHy6n">
<b>本体层</b>：Skill 是什么；</li>
<li data-pid="KtVZ4VgV">
<b>表示层</b>：Skill 如何编码和打包；</li>
<li data-pid="-UAgXYsD">
<b>生命周期层</b>：Skill 如何获取、存储、使用、维护和内化；</li>
<li data-pid="1sTvkkLD">
<b>运行时层</b>：Skill 如何接入终端、工具、多 Agent 和 Harness；</li>
<li data-pid="G61TrVaZ">
<b>治理层</b>：Skill 如何安全可信地分发和执行；</li>
<li data-pid="lSgxeAo5">
<b>应用层</b>：Skill 如何服务机器人、游戏、网页、GUI、OS 和软件工程。</li>
</ul><p data-pid="zgjBzdkt">如果说 Tool 让模型“能做事”，Memory 让模型“记得事”，那么 Skill 让模型开始“会做事”。</p><p data-pid="8d2GS0_e">更准确地说：</p><p data-pid="VaiHQoby"><b>Skill 是 Agent 把经验变成能力的接口。</b></p><p data-pid="JnLYA2xe">它不是一个提示词技巧，也不是一个简单插件，而是未来智能体系统中可复用、可组合、可审计、可进化的程序性基础设施。</p><p data-pid="xfKd1PP4">下一阶段的 Agent 竞争，可能不只是谁的模型更强，也是谁拥有更好的 Skill 生态：</p><p data-pid="dweiHAIP">谁能更快沉淀经验，谁就能更快提升 Agent； 谁能更好治理 Skill，谁就能更安全地部署 Agent； 谁能构建可复用 Skill 基础设施，谁就可能拥有下一代智能体平台的入口。</p><p data-pid="8ZoLzDgL"><b>Agent Skill 的时代，才刚刚开始。</b></p>
