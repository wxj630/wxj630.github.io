<p data-pid="tYwnFvjI">最近 <code>Harness Engineering</code> 这个概念开始火起来。AI和大模型领域发展日新月异，Prompt Engineering、Context Engineering、RAG、Memory、Tool Use、Harness新名词层出不穷，好像每个词都是一套新范式。</p><p data-pid="XKppxDas">但如果把它们放到同一个视角下看，本质其实很简单：</p><p data-pid="zQvtQrzh">大语言模型吐出的每一个 token，都是在某个条件下的概率采样。</p><p data-pid="AtqyKgz7">最朴素的模型是：</p><p data-pid="S6AKpt3V"><code>P(X | θ)</code></p><p data-pid="EjYbSEHT">其中 <code>θ</code> 是模型参数。预训练、微调、RLHF、强化学习，本质上都是在改变 <code>θ</code> 或者改变 <code>θ</code> 的分布。</p><p data-pid="2ebGzSEn">而 Prompt、Context、RAG、Memory、Tool、Harness 做的事情，是另一条路线：</p><p data-pid="a-lno-wL"><code>P(X | θ, C)</code></p><p data-pid="z2RHRzCk">模型参数不变，但我们改变推理时的条件 <code>C</code>。</p><p data-pid="A23nBvaa">所以说要：</p><ol>
<li data-pid="iCEauR8Y">改变模型本身：预训练、微调、强化学习。</li>
<li data-pid="IaFRKQDJ">改变模型推理环境：Prompt、Context、RAG、Memory、Tool、Harness。</li>
</ol><p data-pid="sMaVPzCU">前者是训练，后者是推理环境工程。</p><p data-pid="ylZB9gAl">这也是为什么 AI 工程范式会从 Prompt Engineering 走向 Context Engineering，再走向 Harness Engineering。</p><h2>一、从 Prompt 到 Context，再到 Harness</h2><p data-pid="MHWS0yAI">Prompt Engineering 解决的是：如何把任务说清楚。</p><p data-pid="ffMRK24s">早期我们面对的是问答场景。你输入一句话，模型输出一段回答。于是大家研究角色设定、few-shot、CoT、ReAct，本质是在优化输入表达。</p><p data-pid="L8s04Unz">但当任务从“答一道题”变成“让 Agent 连续几十分钟完成一个真实任务”，Prompt 就不够了。</p><p data-pid="EwsOm8dj">因为很多失败不是模型不会，而是它不知道：</p><ul>
<li data-pid="M12OCbl-">该看什么文件</li>
<li data-pid="Homhovhz">该调用什么工具</li>
<li data-pid="nGt8ui_t">错了以后如何验证</li>
<li data-pid="bjZmRDwx">什么时候应该停止</li>
<li data-pid="z7BIqhbX">哪些经验应该沉淀下来，下次继续用</li>
</ul><p data-pid="UfLvingA">于是 Context Engineering 出现了。它关心的是模型在关键时刻能看到什么，包括用户输入、工具返回、历史对话、检索片段、短期记忆、长期记忆、当前任务状态。</p><p data-pid="bWq-eojD">但只补 Context 仍然不够。</p><p data-pid="ZknNajyg">一个 Coding Agent 真正要稳定工作，还需要运行环境、权限边界、反馈回路、测试机制、日志、版本记录、失败恢复。这就是 Harness Engineering。</p><p data-pid="ROyCBAzX">如果把 Agent 看作一个新入职工程师，Prompt 是任务说明，Context 是你递给他的材料，Harness 是他的电脑、权限、文档、工具链、测试环境和团队规范。</p><p data-pid="_W7k3P1J">真实任务里，决定 Agent 能不能交付的，往往不是“模型会不会写代码”，而是这个工程支架搭得好不好。</p><h3>1.1 为什么 Skill 变得越来越重要</h3><p data-pid="PcrZMLV8">在这个框架里，Skill 是一个很关键但经常被低估的东西。</p><p data-pid="zDyBAiCE">Skill 不是简单的 Prompt 模板。它更像是“被压缩过的工程经验”。</p><p data-pid="tS-DE-Fc">比如一个 Debug Agent，如果只告诉它：</p><blockquote data-pid="GAmiSSlq"> 解决这个崩溃问题。</blockquote><p data-pid="jXaJReVJ">即使你给它日志和代码仓库，它也可能在仓库里盲目搜索，读很多无关文件，然后围绕一个错误假设反复自证。</p><p data-pid="fGJsdovh">但如果你给它一个崩溃分析 Skill：</p><ul>
<li data-pid="ZqMwZTqs">遇到这类崩溃先搜哪些关键字</li>
<li data-pid="Cg1chnCE">优先调用哪个本地分析工具</li>
<li data-pid="RZefHfpK">如何从日志反查调用链</li>
<li data-pid="ad6auwK0">什么时候看 git 历史</li>
<li data-pid="SvUsvwBo">哪些历史案例值得参考</li>
</ul><p data-pid="gmZ56C3H">它的行为会立刻变得更像一个有经验的工程师。</p><p data-pid="MrcXrqVG">这说明 Agent 缺的不是“再解释一遍任务”，而是一条可执行的调查路径。</p><p data-pid="mYfXv_fx">所以我认为，Agent 时代真正有价值的工程资产，不是某一段 prompt，而是可复用、可验证、可进化的 Skill / SOP。</p><p data-pid="o1k-eXnp">问题是：Skill 应该如何进化？</p><h3>1.2 Skill 进化不能靠玄学</h3><p data-pid="V7ShqbCO">现在很多 Agent 系统都有 Memory 或 Skill 机制，但它们的更新方式往往比较粗糙。</p><p data-pid="02WtL-O0">任务成功了，就把经验写进去。 任务失败了，就补一句“以后不要这样”。</p><p data-pid="YxBoMRGK">这有两个问题。</p><p data-pid="jlwOg7MC">第一，经验不一定可靠。一次成功可能只是运气，一次失败也可能只是环境偶然波动。</p><p data-pid="ctj-m25h">第二，Skill 容易膨胀。所有经验都往里写，最后 Skill 变成一堆互相冲突的自然语言碎片，模型反而更难用。</p><p data-pid="SdGe9unV">所以我设计了一个 Bayesian Self-Evolving 算法，把 Skill 当成一个可检验的假设，而不是一段神圣文本。</p><p data-pid="zRBE1_Li">一个 Skill / SOP 可以看作假设 <code>h</code>：</p><blockquote data-pid="UvKCB3Ta"> 在某类任务上下文中，使用这个 Skill 可以提高成功概率。</blockquote><p data-pid="CdtA1pRE">于是我们要估计的是：</p><p data-pid="XCRbpfk3"><code>P(success | θ, C, h)</code></p><p data-pid="6itIsPiM">模型参数 <code>θ</code> 不变，任务上下文 <code>C</code> 不同，Skill 假设 <code>h</code> 会随着证据更新。</p><h2>二、Bayesian Self-Evolving 的核心思路</h2><figure data-size="normal"><img src="/assets/blog/images/09f2d7dae26ea829249e.png" data-size="normal" data-rawwidth="8149" data-rawheight="4369" class="origin_image zh-lightbox-thumb" width="8149" data-original="/assets/blog/images/09f2d7dae26ea829249e.png"><figcaption>Bayesian Agent方法架构图</figcaption></figure><p data-pid="SkT_N5QI">算法很简单：</p><ol>
<li data-pid="2yOG91WR">每个 Skill 维护一个 posterior belief。</li>
<li data-pid="Ox0jFuzO">初始用 Beta prior，例如 <code>Beta(1, 1)</code>。</li>
<li data-pid="75hs54iG">每次任务执行后，记录 action-verified evidence。</li>
<li data-pid="yRVufy_H">成功则提高 <code>alpha</code>，失败则提高 <code>beta</code>。</li>
<li data-pid="uEEpWCuo">同时记录 failure mode、token cost、耗时、适用上下文。</li>
<li data-pid="UtTakQwo">Skill 改写不直接靠主观总结，而是根据 posterior 和 failure mode 触发。</li>
</ol><p data-pid="m9fY5kAG">举例：</p><ul>
<li data-pid="oSOc9mm_">如果连续成功，posterior success 提高，就压缩和强化这条 Skill。</li>
<li data-pid="QPHEgtSl">如果某个上下文成功、另一个上下文失败，就拆分 Skill。</li>
<li data-pid="1ZPi7N1v">如果失败集中在同一类 failure mode，就做局部 patch。</li>
<li data-pid="Aunb98Cn">如果失败压倒成功，就 retire 或重写。</li>
<li data-pid="pBW5Iccn">如果没有足够证据，就保持 exploratory，不急着固化进长期记忆。</li>
</ul><p data-pid="QScRoMjJ">这和传统 Memory 最大的区别是：它不是“把感觉写进记忆”，而是“把验证过的证据写进 posterior”。</p><p data-pid="8k49Y4XH">也就是说，Skill 的进化过程本身变成了一个小型贝叶斯推理过程。</p><h3>2.1 两种使用方式：从零进化，以及增量修复</h3><p data-pid="1MO9Hghh">我把这个算法接到了 GenericAgent 上，并用 <code>deepseek-v4-flash</code> 做了两组实验。</p><p data-pid="wuQPj8ah">第一组是从零开始跑。也就是不给它 GA 之前的失败结果，让 Bayesian Skill 在 benchmark 过程中自己积累证据。</p><p data-pid="87395v5L">第二组是增量模式。这个更有实用价值：假设你已经有一个 Agent，比如 GA，它在 benchmark 上没有达到 100%。Bayesian 模块不推翻原系统，只读取 GA 的成功/失败轨迹，把失败样本变成 evidence，然后只重跑失败题。</p><p data-pid="wNwSHq9V">这相当于把 Bayesian Self-Evolving 当成一个即插即用的修复层。</p><h2>三、实验：GA + deepseek-v4-flash 基线</h2><p data-pid="sYIpoZ1k">原始 GA + <code>deepseek-v4-flash</code> 的结果是：</p><table data-draft-node="block" data-draft-type="table" data-size="normal" data-row-style="normal"><tbody>

<li data-pid="0KWG1pZq">谁能把失败变成可复用证据</li>
<li data-pid="xNOnQ9mz">谁能把经验压缩成可执行 Skill</li>
<li data-pid="l1X-6fAI">谁能让 Skill 在长期任务里不断进化</li>
<li data-pid="o7lCY1jl">谁能用最小 token 成本，把已有 Agent 的成功率继续往上推</li>
</ul><p data-pid="gHI8CxF2">Agent 每一次成功和失败，都不应该只是日志里的噪声，而应该成为下一次推理环境的一部分。贝叶斯方法为我们去建模这一过程提供了有力的工具。</p><p data-pid="qAqz-w6l">我们会把这套 Bayesian Self-Evolving Agent 的代码开源在：</p><a href="http://link.zhihu.com/?target=https%3A//github.com/DataArcTech/Bayesian-Agent" data-draft-node="block" data-draft-type="link-card" data-draft-title="https://github.com/DataArcTech/Bayesian-Agent" class=" external" target="_blank" rel="nofollow noreferrer"><span class="invisible">https://</span><span class="visible">github.com/DataArcTech/</span><span class="invisible">Bayesian-Agent</span><span class="ellipsis"></span></a>
