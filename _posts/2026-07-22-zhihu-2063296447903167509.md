<p data-pid="iC-gq1q4">上一篇《<a href="https://zhuanlan.zhihu.com/p/2055334121686185919" class="internal" target="_blank">高质量 Agent 训练数据，正在怎么被合成？</a>》，里面讲到一个趋势：</p><blockquote data-pid="-1OZRvh-"> Agent 训练数据正在从“问答样本”变成“可执行环境 + 任务指令 + verifier + 轨迹 + reward”。<br> </blockquote><p data-pid="i6BsyZI1">这句话听起来有点抽象。</p><p data-pid="jH9QgJvg">如果你只是训练一个 Chat 模型，一条数据可能是：</p><div class="highlight"><pre><code class="language-text"><span></span>user question -&gt; assistant answer
</code></pre></div><p data-pid="_4S5w9RK">但如果你想训练一个能在终端、代码仓库、Docker 环境里工作的 Agent，普通问答数据就不够了。Agent 真正需要学习的是：</p><ul>
<li data-pid="a6pxqNrx">如何读任务；</li>
<li data-pid="5YfyePrp">如何探索文件系统；</li>
<li data-pid="8KiJsCLg">如何写代码或脚本；</li>
<li data-pid="Iz10Qvj1">如何运行测试；</li>
<li data-pid="6hNmMTGk">如何从报错里恢复；</li>
<li data-pid="-hz38up_">如何在 verifier 约束下交付一个真的能跑通的结果。</li>
</ul><p data-pid="UvTuG1xJ">所以这次 DataArc-SynData-Toolkit 的更新，最重要的不是“多了几种 prompt”，而是补上了一条完整的 Agentic Data 合成链路：</p><blockquote data-pid="Sasdpb6R">
<b>A Scalable and Verified Environment Synthesis Framework for Agent RL Training</b><br> </blockquote><p data-pid="s1A0uZVn">更直白一点说：</p><blockquote data-pid="_JLTDxlP"> 它不再只是合成 instruction / CoT，而是在合成“可执行、可验证、可评测、可产出轨迹”的 Agent 训练环境。<br> </blockquote><p data-pid="C4cjYUMb">本文对应的代码实现已经放在 DataArc-SynData-Toolkit 的 <code>SynAgenticData</code> 分支。代码和运行细节大家可以直接看仓库，本文重点讲方法：怎么通过 prompting 引导大模型合成一整个可验证任务环境，而不是只改写一道题面。</p><a href="http://link.zhihu.com/?target=https%3A//github.com/DataArcTech/DataArc-SynData-Toolkit/tree/SynAgenticData" data-draft-node="block" data-draft-type="link-card" data-draft-title="https://github.com/DataArcTech/DataArc-SynData-Toolkit/tree/SynAgenticData" class=" external" target="_blank" rel="nofollow noreferrer"><span class="invisible">https://</span><span class="visible">github.com/DataArcTech/</span><span class="invisible">DataArc-SynData-Toolkit/tree/SynAgenticData</span><span class="ellipsis"></span></a><figure data-size="normal"><img src="/assets/blog/images/0f2db867c4eee58acb42.png" data-caption="" data-size="normal" data-rawwidth="1600" data-rawheight="900" class="origin_image zh-lightbox-thumb" width="1600" data-original="/assets/blog/images/0f2db867c4eee58acb42.png"></figure><h2>一、为什么普通数据合成不够？</h2><p data-pid="R4Ku1AeN">传统 synthetic data pipeline 通常围绕三个东西转：</p><ol>
<li data-pid="-DrMJeGo">生成一个新 instruction；</li>
<li data-pid="Hb-iIaBK">生成一个参考回答；</li>
<li data-pid="3MMQuVtr">做一些格式、质量、去重过滤。</li>
</ol><p data-pid="V_4eSfDP">这对普通 SFT 很有用，但对 Agent RL 来说有一个根本问题：<b>答案说得像，不代表任务做得成。</b></p><p data-pid="_5eThywS">例如一个 terminal-bench 风格任务，用户可能要求：</p><blockquote data-pid="qsgCGswB"> 修复一个并发 Bash 脚本，使它在多进程同时运行时仍然能原子地更新日志汇总文件。<br> </blockquote><p data-pid="bU2Li0qH">这时候只生成一段“看似合理”的解法没有意义。我们真正关心的是：</p><ul>
<li data-pid="LxUbOt6F">Docker 环境能不能构建？</li>
<li data-pid="HMaGHfDQ">初始文件和输入数据是否完整？</li>
<li data-pid="DAyx8Ly-">Agent 写出的脚本是否真的处理了并发？</li>
<li data-pid="_-hMoE6_">verifier 是否真的覆盖了原子写、排序、重复运行等边界？</li>
<li data-pid="zeyQK86n">oracle solution 是否能通过这套 verifier？</li>
<li data-pid="ZgqpC5bw">下游 Agent 的执行轨迹和 reward 是多少？</li>
</ul><p data-pid="sZliXJ1a">换句话说，Agentic Data 的单位不是一条文本，而是一个任务环境。</p><h2>二、一个 verified env 到底包含什么？</h2><p data-pid="CoajCvVz">这次我们把 terminal-bench 风格任务当作核心目标。一个合成样本不再只是 <code>input/output</code>，而是一整个任务目录。</p><p data-pid="dSh1VmnL">核心 artifact 至少包括：</p><table data-draft-node="block" data-draft-type="table" data-size="normal" data-row-style="normal"><tbody>
<tr>
<th>组成部分</th>
<th>作用</th>
</tr>
<tr>
<td>instruction.md</td>
<td>用户看到的任务描述，必须写清楚所有可验证约束</td>
</tr>
<tr>
<td>输入数据 / fixtures</td>
<td>任务依赖的 CSV、JSON、源码、配置、图片、日志、数据库种子等</td>
</tr>
<tr>
<td>solution/solve.sh</td>
<td>oracle/reference solution，用来证明这个任务有解</td>
</tr>
<tr>
<td>tests/test.sh</td>
<td>verifier 入口，负责执行测试并写入 reward</td>
</tr>
<tr>
<td>tests/test_outputs.py</td>
<td>具体断言逻辑，验证输出是否满足 instruction</td>
</tr>
<tr>
<td>environment/Dockerfile</td>
<td>运行环境，必要时安装 apt/pip/npm 等依赖</td>
</tr>
<tr>
<td>helper/starter files</td>
<td>被 instruction、solution 或 tests 依赖的辅助文件</td>
</tr>
</tbody></table><p data-pid="V-1O0BP2">这里有一个很容易犯错的点：</p><blockquote data-pid="ItOMNTyA"> 不能只改 instruction 和输入数据。<br> </blockquote><p data-pid="h8nqQKMY">如果任务描述变了，oracle solution 和 tests/verifier 也必须同步变化。否则就会出现非常糟糕的数据污染：</p><ul>
<li data-pid="6zFzrNZB">Agent 按新 instruction 做了，但旧 tests 还在测旧任务；</li>
<li data-pid="BGd6zjyF">tests 改了，但 oracle solution 没改，任务根本不可解；</li>
<li data-pid="yda54qo4">数据改了，但 verifier 仍然在断言旧 expected output；</li>
<li data-pid="z227vycy">Dockerfile 没改，solution/tests 在环境里跑不起来。</li>
</ul><p data-pid="DuHkLZlV">所以正确的心智模型是一个“一致性闭包”：</p><div class="highlight"><pre><code class="language-text"><span></span>instruction + input data + solution + tests + environment
</code></pre></div><p data-pid="E286XzU8">任何一处变了，其他几处都要重新检查。最终能不能进训练集，不看模型自称正确，而看 oracle solution 在新 tests 下跑出来的 reward。</p><h2>三、方法流程：让模型合成完整 env，而不是一条题面</h2><p data-pid="0J2qjoPR">这次的核心，不是多写几个脚本，而是把大模型的输出空间从“生成一段回答”约束成“生成一个可执行任务环境”。</p><p data-pid="LfWZndG9">整体流程是：</p><div class="highlight"><pre><code class="language-text"><span></span>seed terminal task
  -&gt; method-specific synthesis prompt
  -&gt; full task artifact JSON
  -&gt; static validation
  -&gt; materialize terminal-bench directory
  -&gt; Harbor oracle/gold solution validation
  -&gt; repair if failed
  -&gt; accepted verified task
  -&gt; Terminus-2 rollout
  -&gt; trajectory + reward
</code></pre></div><p data-pid="B_XA844H">其中最关键的是两级验证。</p><p data-pid="VQ7P_8wp">第一级是静态验证，比如：</p><ul>
<li data-pid="qMnMmvGL">是否包含必需文件；</li>
<li data-pid="_54UHR6_">路径是否安全；</li>
<li data-pid="AVPB1bem">是否误带 terminal-bench canary；</li>
<li data-pid="JqflnzIJ">Dockerfile 是否用了不稳定的 <code>:latest</code>；</li>
<li data-pid="j4QkLX2f">
<code>tests/test.sh</code> 是否一定会写 <code>/logs/verifier/reward.txt</code>；</li>
<li data-pid="tNuJNt1r">是否在 verifier runtime 下载外部安装脚本；</li>
<li data-pid="upExk-5o">是否把 task root 的 tests/solution 直接 COPY 进 Docker build context。</li>
</ul><p data-pid="JCU9pbNh">第二级是 gold solution 验证：</p><blockquote data-pid="iIuzwDyh"> 把生成出来的任务真的物化成 terminal-bench 目录，然后用 Harbor 跑 oracle solution，只有 reward=1 才算 accepted。<br> </blockquote><p data-pid="QaX2vNxP">这也是我认为这次更新最有价值的地方：它把“数据生成”从 prompt 工程，推进到了 verifier-backed environment synthesis。</p><h2>四、四种合成方法：不只是换题面</h2><p data-pid="wt3HEJoD">这次我们扩展了Dataarc-Syndata-Toolkit的四种数据合成方法到Agentic任务/环境合成：</p><table data-draft-node="block" data-draft-type="table" data-size="normal" data-row-style="normal"><tbody>

</tr>

<li data-pid="4CCQ3Xzp">instruction；</li>
<li data-pid="c3jo-nFf">输入数据；</li>
<li data-pid="jSg294E5">oracle solution；</li>

<li data-pid="DuemTzaW">

<li data-pid="qkt5r8eO">
<code>breadth</code> 是“保留数据领域，但换成邻近任务类型”。</li>
</ul><p data-pid="jjTcUd7U">更重要的是，这几条不是只改了题面。每条任务都同步改了 instruction、fixtures、solution 和 tests，并通过 oracle verification。</p><h2>八、一些真正难的任务：Agent 过不了，但训练价值很高</h2><p data-pid="qa4W6bur">如果只看成功案例，很容易产生一个错觉：合成任务是不是都偏简单？</p><p data-pid="qBR2zZot">实际上并不是。</p><p data-pid="nQwdRSUf">我们专门找了一些 Terminus-2 不怎么过的任务族：</p><figure data-size="normal"><img src="/assets/blog/images/6f8a40bec357bdc30775.png" data-caption="" data-size="normal" data-rawwidth="1600" data-rawheight="900" class="origin_image zh-lightbox-thumb" width="1600" data-original="/assets/blog/images/6f8a40bec357bdc30775.png"></figure><table data-draft-node="block" data-draft-type="table" data-size="normal" data-row-style="normal"><tbody>

<li data-pid="wVdSKPSQ">并发；</li>
<li data-pid="eIjBp9Y8">锁；</li>
<li data-pid="G3YOgWw9">atomic write；</li>
<li data-pid="WVM4Tqsf">去重；</li>
<li data-pid="9oNt67c_">排序；</li>
<li data-pid="2m5NnNVa">多次运行一致性。</li>
</ul><p data-pid="gDIyxt8c">Agent 很容易写出一个“看起来能跑”的 Bash 脚本，但 verifier 一跑边界就暴露出来。</p><h3>PGN chess repair：规则推理 + 精确 JSON 输出</h3><p data-pid="cR80-q0D">原始任务要求修复 corrupted PGN、分析棋局、解 puzzles，reward 0.533。</p><p data-pid="yTfBudDj">合成任务里：</p><ul>
<li data-pid="0vWw8ktw">
<code>few_shot</code> 简化成 chess validator，reward=1；</li>
<li data-pid="cY-c5seF">
<code>self_instruct</code> 简化成单局 corrupted game + 两个 puzzle，reward=0.7；</li>
<li data-pid="MAe8CyEU">
<code>depth</code> 加 forced mate 的 <code>mate_in</code> 精确步数，reward=0；</li>
<li data-pid="3O5cL1tf">
<code>breadth</code> 改成 FEN 是否被将军，reward=0。</li>
</ul><p data-pid="7D4tJeFO">这说明规则推理、结构化输出和领域知识叠在一起时，Agent 表现非常不稳定。尤其 <code>mate_in</code> 这种精确约束，一加就明显变难。</p><h2>九、为什么这对 Agent RL Training 重要？</h2><p data-pid="D8Y0ZcGu">我觉得这个框架真正有价值的地方，不只是“能生成 400 条任务”。</p><p data-pid="JvoNf6cp">更关键的是，它把 RL 需要的几个东西放到了一条链路里：</p><h3>1. 可执行任务环境</h3><p data-pid="jPrRHmnP">每条任务都是一个 terminal-bench 风格目录，而不是一段不可验证文本。</p><p data-pid="iFXXT1eC">这意味着它可以被 harness 调用，可以在 Docker 里跑，可以复现 reward。</p><h3>2. Oracle-backed verification</h3><p data-pid="zLKJx_Bx">生成任务不是靠模型自评，而是要用 oracle solution 通过 tests。</p><p data-pid="bAXhVrmv">这能过滤掉大量“题面和测试不一致”“任务无解”“环境跑不起来”的坏样本。</p><h3>3. Downstream agent trajectory</h3><p data-pid="qVxS28w2">Terminus-2 跑完后，每个 trial 都会生成 trajectory，包括多轮行动、命令输出、失败、恢复和最终 verifier reward。</p><p data-pid="bcfa2zTb">这类 trajectory 可以用于：</p><ul>
<li data-pid="LhgshEw9">SFT：把成功轨迹转成监督数据；</li>
<li data-pid="SenBmyKo">RL：用完整 action sequence 和 reward 做策略优化；</li>
<li data-pid="PSxALi3_">debugging：定位 agent 在哪一步偏航；</li>
<li data-pid="YuJ20wEr">curriculum：根据任务族、失败模式和 reward 分布安排训练顺序。</li>
</ul><h3>4. 失败样本也有价值</h3><p data-pid="F39YLf4y">在普通 SFT 里，失败样本经常被丢掉。</p><p data-pid="eGf_IAaA">但在 Agent RL 里，失败很有价值。比如：</p><ul>
<li data-pid="BVBbCvvS">systemd 系列全挂，说明系统服务配置能力薄弱；</li>
<li data-pid="ksvqGGRT">Bash 并发脚本全挂，说明 shell concurrency 和 atomicity 是短板；</li>
<li data-pid="HJIJaOtQ">TSL 任务全挂，说明抽象测试规格解析能力不足；</li>
<li data-pid="1xVngVSa">chess 任务不稳定，说明规则推理和精确结构化输出仍然薄弱。</li>
</ul><p data-pid="gg2_Y0tq">这些失败不是噪声，而是训练信号。</p><h2>十、怎么通过 Prompting 做任务/环境合成？</h2><p data-pid="pVDZu6jd">如果只给模型一句“帮我改写这个任务”，它大概率只会改 instruction。</p><p data-pid="1MHQzY4F">但 agentic env synthesis 不是改写题面。我们真正要 prompt 的，不是一个 answer generator，而是一个同时扮演四个角色的模型：</p><ol>
<li data-pid="u8RxAQrI">任务设计者：决定新任务要求什么；</li>
<li data-pid="bKkvf5-2">输入数据生成器：构造和任务一致的 fixtures；</li>
<li data-pid="_ko3wh2G">oracle solution 作者：写出一份可执行参考解，证明任务有解；</li>
<li data-pid="NFJMeeVf">verifier 作者：写出 tests，检查 Agent 的最终结果是否真的满足 instruction。</li>
</ol><p data-pid="BqUj3Af2">所以 prompt 不能只描述“生成什么样的新任务”，还要描述“哪些 artifact 必须一起变化”。</p><p data-pid="gRvWGbaa">我现在更倾向于把这个 prompt 拆成三层。</p><h3>1. Seed Context：把原任务拆给模型看</h3><p data-pid="-C0uDXXL">第一层是 seed context。不要只给原始 instruction，而是把一个任务环境拆成模型能理解的结构：</p><ul>
<li data-pid="-alVno7-">原始任务描述；</li>
<li data-pid="Mepdsva7">原始文件树；</li>
<li data-pid="VPiXW3wm">关键输入数据片段；</li>
<li data-pid="k4-p7tTA">oracle solution 的核心逻辑；</li>
<li data-pid="tp9qmc6Y">verifier/tests 的核心断言；</li>
<li data-pid="uOG7Oqxr">Docker/environment 约束；</li>
<li data-pid="0shAhoLB">原任务需要的能力，比如 CSV/JSON merge、Bash concurrency、systemd 配置、测试用例生成等。</li>
</ul><p data-pid="RlWb2Wxd">这一步的作用是让模型知道：原任务不只是一段文字，而是一个由 instruction、data、solution、tests、environment 组成的闭包。</p><h3>2. Synthesis Action：明确这次到底怎么变</h3><p data-pid="1Yc_Zh7l">第二层是 synthesis action，也就是这次合成采用哪种“变化原语”。</p><table data-draft-node="block" data-draft-type="table" data-size="normal" data-row-style="normal"><tbody>

<li data-pid="v2umvHRB">
<code>few_shot</code> 可以换成大学薪资字段 merge；</li>
<li data-pid="HwfoZUeY">

<li data-pid="xS3VPMKh">

<li data-pid="RK55h3ts">
<code>breadth</code> 可以横向变成 top salary extractor。</li>
</ul><p data-pid="DS4EZfE0">它们共享一个要求：只要任务变了，fixtures、oracle solution、tests 也必须跟着变。</p><h3>3. Output Contract：让模型输出完整环境，而不是自然语言解释</h3><p data-pid="VnWqZ2Uh">第三层是 output contract。这里要非常硬。</p><p data-pid="xICXWs9Q">模型不能只输出“新任务描述”，而要输出一个完整的 environment spec：</p><div class="highlight"><pre><code class="language-text"><span></span>task_id
instruction
files / fixtures
oracle solution
tests / verifier
environment assumptions
metadata: source seed, synthesis method, changed skills
</code></pre></div><p data-pid="-0qN92yT">同时 prompt 里要加一些强约束：</p><ul>
<li data-pid="adOy05UT">instruction 里提到的输入文件，fixtures 必须真的存在；</li>
<li data-pid="uJfMjAVb">tests 检查的输出文件，instruction 必须明确要求生成；</li>
<li data-pid="-5z-apyf">oracle solution 必须只依赖任务环境内的文件；</li>
<li data-pid="U_9jdb5I">tests 不能偷偷检查 solution 路径，只能检查 Agent 产物；</li>
<li data-pid="Ir6Pjfzb">verifier 必须覆盖核心约束，而不是只检查文件存在；</li>
<li data-pid="aLgR3Zwz">Docker/environment 不能依赖不稳定的 runtime 下载；</li>
<li data-pid="itNwq_cF">如果改了数据 schema，solution 和 tests 里的字段名也要同步改。</li>
</ul><p data-pid="7aFw-uCa">我觉得这就是 agentic data synthesis 和普通 instruction synthesis 最大的区别。</p><p data-pid="-HJwIebO">普通 instruction synthesis 的 prompt 目标是“生成一个问题”。<br>Agentic env synthesis 的 prompt 目标是“生成一个可执行问题系统”。</p><h3>4. Repair Prompt：验证失败后，不要让模型重写一切</h3><p data-pid="vuCb1GEf">还有一个很重要的技巧：repair prompt。</p><p data-pid="GMcNCQ-O">模型第一次生成的任务很容易出现小错，比如：</p><ul>
<li data-pid="59vpKi02">tests 断言了旧字段；</li>
<li data-pid="BROxHmSR">solution 输出路径和 instruction 不一致；</li>
<li data-pid="rUFOPRdg">某个 fixture 文件漏了；</li>
<li data-pid="6S1SEeQx">Docker 环境缺依赖；</li>
<li data-pid="hAGOCgKI">verifier 没有正确写 reward。</li>
</ul><p data-pid="U6RkbHRF">这时候不要简单说“重新生成一个任务”。更好的方式是把失败日志、静态检查结果、gold solution reward 和相关 artifact 片段喂回模型，让它做定向修复：</p><blockquote data-pid="Gr74GPqU"> 保持任务意图不变，只修复导致 verification failure 的最小不一致。<br> </blockquote><p data-pid="T3pNH3mA">这会显著减少任务漂移。否则模型很容易在 repair 阶段把任务改成另一个东西，最后虽然通过了验证，但已经不是原本想合成的那类训练样本了。</p><p data-pid="08Ci8G8r">所以整套 prompting 的核心可以总结成一句话：</p><blockquote data-pid="vEVWsoCB"> 不是 prompt 模型“出一道题”，而是 prompt 模型生成一个 instruction、data、solution、tests、environment 彼此一致的可验证任务环境。<br> </blockquote><h2>十一、目前还有哪些限制？</h2><p data-pid="YPODy9pn">这个方向很有前景，但坑也不少。</p><h3>1. 生成任务必须严防不一致</h3><p data-pid="MIHrwXTt">最危险的问题永远是：</p><blockquote data-pid="vHakyNI-"> instruction 改了，但 solution/tests 没同步。<br> </blockquote><p data-pid="SNBraT3J">所以我更倾向于把这类系统叫 verified env synthesis，而不是简单叫 task augmentation。因为“验证”不是后处理小步骤，而是数据是否能用的核心定义。</p><h3>2. Docker / apt / pip / npm 网络问题是真实工程成本</h3><p data-pid="h2Gn9FQu">Agentic env 合成不是只跑 LLM API。</p><p data-pid="fqF4t0LD">它还要构建 Docker、安装依赖、跑 tests。国内网络下，apt、pip、npm、Docker base image 都可能成为不稳定因素。</p><p data-pid="OHLqDHTC">所以生成 prompt 和 Dockerfile static validation 里需要显式处理镜像源、禁止 runtime 下载外部安装脚本、避免 <code>:latest</code>、避免不稳定 bootstrap URL。</p><h3>3. breadth 可能变简单</h3><p data-pid="cIklCKcv"><code>evol-breadth</code> 的目标是扩展任务空间，但如果不控制距离，它可能把一个 hard domain 变成 unrelated easy task。</p><p data-pid="tiFfDzdS">比如 TSL 测试生成横向变成 MD5 hash，Agent 过了，但它对原始 TSL 难点的覆盖就弱了。</p><p data-pid="Xje7ioJs">后续需要引入 task-distance 或 skill taxonomy，控制 breadth 的跨度。</p><h3>4. downstream missing 也要单独分析</h3><p data-pid="ZiHHhri9">Terminus-2 的结果里有些任务是 missing，不是 verifier 明确 reward=0。这可能来自超时、网络、环境构建、API 调用等问题。</p><p data-pid="CCUWWSMS">在训练数据筛选时，missing、timeout、reward=0、partial reward 应该分开看。</p><h3>5. verifier 质量决定上限</h3><p data-pid="ABDOdayx">如果 tests 写得弱，任务很容易被“投机解”通过。</p><p data-pid="Jm-Mf4M2">如果 tests 写得太强但 instruction 没写清楚，Agent 又会被不公平地惩罚。</p><p data-pid="PDwv1V9S">因此 verifier synthesis 本身也是一个核心研究问题。</p><h2>十二、总结</h2><p data-pid="Ls9l_Z-c"> DataArc-SynData-Toolkit 这次更新的内容，可以概括为三句话。</p><p data-pid="IVwmf5K4">第一，数据合成的单位变了。</p><p data-pid="Jp3tLVm2">以前合成的是样本，现在合成的是环境。</p><p data-pid="Avg0Xjrg">第二，质量定义变了。</p><p data-pid="dd4bYBCK">以前看回答像不像，现在看 oracle solution 能不能在 Docker 环境里通过 verifier。</p><p data-pid="b2GNRym_">第三，训练信号变了。</p><p data-pid="SOcoAWo4">以前主要拿成功答案做 SFT，现在可以拿完整 trajectory、reward、failure mode 做 SFT、RL 和 curriculum。</p><p data-pid="rAD1p51w">所以我更愿意把它叫做：</p><div class="highlight"><pre><code class="language-text"><span></span>Scalable and Verified Environment Synthesis Framework
</code></pre></div><p data-pid="Yxsw1p2P">它不是替代 terminal-bench、Harbor 或 Terminus-2，而是把这些能力串起来，让我们可以从一批 seed tasks 出发，规模化地产生 verified environments，再让下游 Agent 真实执行，收集轨迹和 reward。</p><p data-pid="nOkkv13_">这件事对 Agent RL Training 很关键。</p><p data-pid="Yy9tRki9">因为未来的 Agent 模型，不能只靠“看过正确答案”变强。</p><p data-pid="D8SsIn9V">它还需要在大量可执行环境里反复尝试、失败、被 verifier 惩罚、再从轨迹中学习。</p><p data-pid="Ob0zzjlF">而 verified env synthesis，就是给这个训练循环持续供给任务燃料的一套基础设施。</p><h2>第三篇预告：Envs-FORGE，下一条任务该合成谁？</h2><p data-pid="vrV4GrnT">这一篇主要讲的是工程闭环：怎么从 seed task 出发，规模化生成 verified environment，并把它接到 Harbor / Terminus-2 里跑出 trajectory 和 reward。</p><p data-pid="PyKyRuvn">但真正进入 Agent RL 训练之后，会立刻遇到一个更硬的问题：</p><blockquote data-pid="XHaugvki"> 如果我已经能合成很多任务，下一条到底应该合成什么？<br> </blockquote><p data-pid="0Lht26eM">不是所有 verified task 都同样有训练价值。太简单的任务，Agent 已经会了；太难的任务，Agent 可能完全学不到；真正有价值的，往往是卡在当前 Agent learning frontier 附近的任务：有挑战，但不是纯送死；会失败，但失败里有可学习的结构。</p><p data-pid="cYTSxcQ9">所以下一篇我会介绍我们正在做的 <b>Envs-FORGE</b>：<b>F</b>rontier-<b>O</b>ptimized <b>R</b>eward-<b>G</b>rounded <b>E</b>nvironment Synthesis for Agent RL</p><blockquote data-pid="PEUUVv3w"> 把 Agent 环境合成从 prompt baseline，推进到 reward-grounded、frontier-optimized 的优化问题。<br> </blockquote><p data-pid="sQJHAYlo">它不是再多加一个 prompt 模板，而是尝试把“该合成什么”写成一个可求解的优化问题。</p><p data-pid="YGZFDmW0">建模上，我们会把一次环境合成拆成几个离散决策变量：选哪个 seed task、用哪种 synthesis action、覆盖哪些 skill subgraph。目标函数不是简单追求“越难越好”或“越像原题越好”，而是让合成后的任务尽量落在当前 Agent 的 learning frontier 附近，比如 reward 既不是接近 1 的已掌握任务，也不是接近 0 的不可学习任务，而是更接近 0.5 左右、有训练梯度的任务。约束则来自 verified env synthesis 本身：合成结果必须通过 oracle verification，同时还要满足方法覆盖、技能覆盖和生成预算等限制。</p><p data-pid="xIcHs4MU">一个非常简化的形式可以写成：</p><p><br></p><p data-pid="sKM4UN1_"><img eeimg="2" src="/assets/blog/images/b211a8104d820d36bd1b.svg" alt=" \begin{aligned} \max_{x_{i,a}, z_s}\quad &amp; \sum_{i,a} x_{i,a}\bigl(1 - 2|\hat r_{i,a} - 0.5|\bigr)   + \lambda \sum_s z_s \\ \text{s.t.}\quad &amp; \sum_{i,a} x_{i,a} = B \\ &amp; x_{i,a} \le v_{i,a} \\ &amp; z_s \le \sum_{i,a} x_{i,a} g_{i,a,s} \\ &amp; x_{i,a}, z_s \in \{0,1\} \end{aligned} "></p><p data-pid="DEK26D1V">这里 <img eeimg="1" src="/assets/blog/images/d5d38fa7a2db609b8d1e.svg" alt="i"> 是 seed task，<img eeimg="1" src="/assets/blog/images/2f37dd7557a3f386e03b.svg" alt="a"> 是 synthesis action，<img eeimg="1" src="/assets/blog/images/122d13a23c71c775694a.svg" alt="x_{i,a}"> 表示是否选择“对 seed <img eeimg="1" src="/assets/blog/images/d5d38fa7a2db609b8d1e.svg" alt="i"> 使用 action <img eeimg="1" src="/assets/blog/images/2f37dd7557a3f386e03b.svg" alt="a">”这次合成，<img eeimg="1" src="/assets/blog/images/bdbf9f27a75fd1c51d48.svg" alt="\hat r_{i,a}"> 是对合成后任务 reward 的估计，<img eeimg="1" src="/assets/blog/images/2fc251a75871d969dafb.svg" alt="v_{i,a}"> 表示这条候选是否满足 verified constraint，<img eeimg="1" src="/assets/blog/images/ea77f1e3175e60bc9190.svg" alt="g_{i,a,s}"> 表示它是否覆盖 skill <img eeimg="1" src="/assets/blog/images/a5aa239a4ee5c34a3e49.svg" alt="s">，<img eeimg="1" src="/assets/blog/images/78f98c36866bdc70bc69.svg" alt="B"> 是合成预算。前一项把任务推向 learning frontier，后一项鼓励 skill coverage。</p><p data-pid="wuJR3LGp">这样一来，<code>few_shot</code>、<code>self_instruct</code>、<code>evol-depth</code>、<code>evol-breadth</code> 不再只是四个并列 baseline，而可以看成这个优化问题里的不同 action choice；现有启发式方法是它的特例，Envs-FORGE 则进一步尝试用 reward estimate 和整数优化来选择更值得合成的任务。</p><p data-pid="G3Fhy22i">它会回答三个问题：</p><ol>
<li data-pid="nt3jmXoR">怎么用当前 Agent 在 seed tasks 上的 reward，估计任务是不是在 learning frontier 附近？</li>
<li data-pid="S-7VxIjq">怎么把 <code>few_shot</code>、<code>self_instruct</code>、<code>evol-depth</code>、<code>evol-breadth</code> 这些 baseline 统一进一个优化框架？</li>
<li data-pid="K-d3-fYS">怎么在生成前选择 seed、projection action 和 skill subgraph，而不是盲目把所有任务都扩一遍？</li>
</ol><p data-pid="3ZkhxStu">如果说这篇文章的关键词是：</p><div class="highlight"><pre><code class="language-text"><span></span>Scalable and Verified Env Synthesis
</code></pre></div><p data-pid="3HxIPNZo">那下一篇的关键词就是：</p><div class="highlight"><pre><code class="language-text"><span></span>Frontier-Optimized Env Synthesis
</code></pre></div><p data-pid="YyRqfkIE">也就是：不只让 Agent 有题可做，而是让它持续遇到“刚好值得学”的题。</p><p data-pid="aZOHdVXK">这会是这组文章里最接近方法论文的一篇：从经验驱动的数据合成，走向可建模、可估计、可优化的 Agent learning frontier。</p>
