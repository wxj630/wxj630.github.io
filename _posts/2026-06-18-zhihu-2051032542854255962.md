<p data-pid="YHt9rPi_">我们有什么证据说明 Agent skill evolving 真的需要 Bayesian belief？</p><p data-pid="eT9KqiVL">上一篇文章里，我讨论了一个问题：</p><p data-pid="ISonFwM3">Agent skill evolving 为什么需要贝叶斯？我直接进化不就行了吗？</p><p data-pid="r6Ae042I">这个问题很合理。</p><p data-pid="W_HbOvKC">因为如果一个方法最后只是“错了就改 prompt / 改 skill”，那它确实不一定需要叫 Bayesian。它最多是一个 failure-driven repair loop。</p><p data-pid="lpYjbVGt">所以这篇文章不继续停留在概念层面，而是回答一个更直接的问题：</p><p data-pid="ktYYwrpg">我们有什么证据说明 Agent skill evolving 真的需要 Bayesian belief？</p><p data-pid="SBtuzCoG">我的回答是：我们有两层保证。</p><p data-pid="10N1VOPG">第一层是实验保证：在 RealFin-Bench 上，Bayesian skill evolving 相比 frequentist 直接进化更稳。</p><p data-pid="CRBiyAMt">第二层是理论保证：在小样本、高成本、强不确定性的 agent 任务里，Bayesian posterior mean 在 posterior squared risk 意义下不劣于 frequentist estimate。</p><p data-pid="loESHPfo">这两层合起来，才是我们说 Bayesian-Agent 有价值的原因。</p><blockquote data-pid="VCnCLDQQ">论文地址：<a href="http://link.zhihu.com/?target=http%3A//arxiv.org/abs/2606.08348" data-icon-name="zhicon_icon_24_link" class=" external" target="_blank" rel="nofollow noreferrer"><span class="invisible">http://</span><span class="visible">arxiv.org/abs/2606.0834</span><span class="invisible">8</span><span class="ellipsis"></span></a>GitHub：<a href="http://link.zhihu.com/?target=https%3A//github.com/DataArcTech/Bayesian-Agent" data-icon-name="zhicon_icon_24_link" class=" external" target="_blank" rel="nofollow noreferrer"><span class="invisible">https://</span><span class="visible">github.com/DataArcTech/</span><span class="invisible">Bayesian-Agent</span><span class="ellipsis"></span></a>
</blockquote><h2>一、先看实验：Bayesian vs Frequentist</h2><p data-pid="HOXZJqlG">我们做了一个对照实验。</p><p data-pid="nDUYxJM7">任务是 RealFin-Bench，一共 40 个金融 agent 任务。它不是简单问答，而是要求 agent：</p><ul>
<li data-pid="YeLnJm7A">读取金融数据；</li>
<li data-pid="RalI08T6">计算 MACD、RSI、KDJ、Bollinger 等指标；</li>
<li data-pid="HbHA0tZq">处理空字段、缺失值和异常数据；</li>
<li data-pid="laPVmPw_">按严格格式写出结果文件；</li>
<li data-pid="CFLyiSv3">通过 verifier 的逐项检查。</li>
</ul><p data-pid="REBZyXPJ">这个 benchmark 很适合测试 skill evolving，因为 agent 失败时，我们不只是知道“错了”，还能看到它到底错在哪里。</p><p data-pid="R8anI12U">比如是没有写输出文件，是空字段导致计算崩溃，是输出格式不对，还是某个指标条件漏算了。</p><h3>1.1 两种 evolving 方法的区别</h3><p data-pid="0oOfObDH">Frequentist control 的思路很直接：</p><div class="highlight"><pre><code class="language-text"><span></span>q_F = S / n
</code></pre></div><p data-pid="I8FZjpKh">也就是用成功次数除以总观察次数，作为某个 skill 或某类行为的可靠性估计。</p><p data-pid="6FNp1_FF">这个方法非常自然。</p><p data-pid="NwankgoY">如果样本足够多，它也很好。</p><p data-pid="UvBOFKu2">但 agent skill evolving 的麻烦在于，我们往往没有很多样本。一个 benchmark 可能只有几十个 case；真实业务中的失败更少，而且每个 case 都很贵。</p><p data-pid="jJO92sLn">Bayesian-Agent 的做法不是只看经验频率，而是维护一个 belief：</p><div class="highlight"><pre><code class="language-text"><span></span>P(skill quality | evidence)
proportional to
P(evidence | skill quality) P(skill quality)
</code></pre></div><p data-pid="x5L1Y9bD">每次 agent 执行后，我们把轨迹、成功失败、failure mode、token cost、latency、metadata 等信息作为 evidence，更新 skill belief。</p><p data-pid="wDZaJK_g">这个 belief 会影响后续决策：</p><ul>
<li data-pid="fCPDn6kM">哪些 skill/SOP 更值得保留；</li>
<li data-pid="AK38gdp4">哪些 failure mode 只是偶然失败；</li>
<li data-pid="kuC95hsz">哪些 failure mode 已经重复出现，应该触发 patch；</li>
<li data-pid="H0jp8LCH">什么时候 rewrite，什么时候先观望；</li>
<li data-pid="0JtkLsLs">如何避免一次失败就把 skill 改得过拟合。</li>
</ul><h3>1.2 实验结果</h3><p data-pid="rS_jjIdo">下面是 RealFin-Bench 的 Bayesian vs Frequentist 对照结果。</p><table data-draft-node="block" data-draft-type="table" data-size="normal" data-row-style="normal"><tbody>

<li data-pid="D2FD_qDT">模型忘了写文件；</li>
<li data-pid="yVOuMqK0">计算脚本中途崩了；</li>
<li data-pid="7mDXKgAx">工具调用轮次不够；</li>
<li data-pid="6oFpiAvh">数据字段没处理好；</li>
<li data-pid="e8-B_kzA">输出路径理解错了。</li>
</ul><p data-pid="QUb4Pd2q">所以重复 fail mode 的出现，不代表系统完全没改，而是说明同一个粗粒度 failure mode 在不同任务里还会以不同根因反复出现。</p><p data-pid="uiTq1G_a">Bayesian 的优势不是“神奇地一次 patch 全修好”，而是对这些重复出现的失败更保守、更结构化地累计证据。</p><p data-pid="ybnjO39y">在实验里，Bayesian skill evolving 更稳定地保留了几类 guardrails：</p><ul>
<li data-pid="mOjzMZiA">先保证 output file 必须存在；</li>
<li data-pid="PD-C6tB1">空字段不能让计算直接崩；</li>
<li data-pid="P1aOh6CC">多指标任务要拆成 verifier predicate 逐项满足；</li>
<li data-pid="xX_g014t">failure mode 重复出现后，再触发更强的 skill patch。</li>
</ul><p data-pid="5rPjJTGd">这就是实验层面的第一个保证：</p><p data-pid="7GAhnV_t">Bayesian 不是“看到错就改”，而是把失败轨迹转成 evidence，再用 evidence 更新 skill belief。</p><p data-pid="iIblSjuC">它解决的不是“永远不再出现同类错误”，而是让系统在重复错误面前有更稳的证据累计和改写决策。</p><h2>二、再看理论：为什么小样本下 frequentist 会抖？</h2><p data-pid="AdXwhtFI">理论部分可以连成一条链：</p><p data-pid="xStf4U3H">frequentist 在小样本下容易抖；</p><p data-pid="0eQnjVYO">Bayesian 用 posterior mean 做平滑；</p><p data-pid="vIwlz17m">在平方损失下，posterior mean 有一个“不劣于”经验频率的风险保证。</p><p data-pid="91PfcbCy">先看 frequentist。</p><p data-pid="Qh93XlG5">假设某个 skill 的真实成功率是 <code>p</code>，观察到 <code>S</code> 次成功，总共执行 <code>n</code> 次。</p><p data-pid="bh4m9hdm">Frequentist 最自然的估计是：</p><div class="highlight"><pre><code class="language-text"><span></span>q_F = S / n
</code></pre></div><p data-pid="ddkWU5sv">这个估计在大样本下很好。</p><p data-pid="_yB2rRAE">但 agent skill evolving 的问题是：我们通常没有大样本。</p><p data-pid="1BaRAN3G">一个 benchmark 可能只有几十个任务，一个真实业务 failure mode 可能一周才出现几次。</p><p data-pid="g4Tcq0oP">经验频率估计的方差是：</p><div class="highlight"><pre><code class="language-text"><span></span>Var(q_F) = p(1 - p) / n
</code></pre></div><p data-pid="kVznZAzr">当 <code>n</code> 很小时，这个方差会很大。</p><p data-pid="8bf57Spn">只观察 1 次时尤其明显：</p><ul>
<li data-pid="pzdBaqgE">成功一次，<code>q_F = 1</code>；</li>
<li data-pid="hOmOsvLI">失败一次，<code>q_F = 0</code>。</li>
</ul><p data-pid="kscA80pZ">如果直接拿这种极端估计指导 skill rewrite，就容易出现两个问题：</p><ul>
<li data-pid="f6abtJg7">一次偶然成功，让系统过度相信一个 skill；</li>
<li data-pid="i0B8ppd4">一次偶然失败，让系统过度改写一个 skill。</li>
</ul><p data-pid="ofBlefYj">这就是小样本下“直接进化”的不稳定来源。</p><h3>2.1 Bayesian 如何缓解？</h3><p data-pid="rNIaD0lf">Bayesian 的做法不是否定经验，而是让经验和先验一起说话。</p><p data-pid="3uCIF9fI">最简单的情况，可以把 skill 成功率建模成 Beta-Bernoulli：</p><div class="highlight"><pre><code class="language-text"><span></span>p ~ Beta(alpha_0, beta_0)
</code></pre></div><p data-pid="YAlccmoO">观察到 <code>S</code> 次成功、<code>F</code> 次失败后，后验是：</p><div class="highlight"><pre><code class="language-text"><span></span>p | evidence ~ Beta(alpha_0 + S, beta_0 + F)
</code></pre></div><p data-pid="0EZs_ff3">后验均值，也就是 Bayesian estimate，可以写成：</p><div class="highlight"><pre><code class="language-text"><span></span>q_B = E[p | evidence]
    = (alpha_0 + S) / (alpha_0 + beta_0 + S + F)
</code></pre></div><p data-pid="4qFSyd8W">它和 <code>q_F = S / n</code> 最大的区别是：<code>q_B</code> 不会在小样本下直接跳到 0 或 1。</p><p data-pid="wViHNYpK">先验 <code>alpha_0, beta_0</code> 会提供 smoothing。</p><p data-pid="3zG6_Ydx">当观察很少时，posterior 更保守；当观察越来越多时，数据逐渐主导，Bayesian 估计也会靠近 frequentist 估计。</p><p data-pid="MF1tXGp5">所以 Bayesian 不是反经验，而是：</p><p data-pid="CReUEjcn">在样本少时不盲信经验；在样本多时让经验说话。</p><h3>2.2 理论保证：Bayesian 不劣于 Frequentist</h3><p data-pid="ZuLzLQDu">论文里给出了一个简洁的理论结论。</p><p data-pid="Pl-aFORF">设 <code>q_F</code> 是经验频率估计，<code>q_B</code> 是 Bayesian posterior mean。在平方损失下：</p><div class="highlight"><pre><code class="language-text"><span></span>E[L(q_F, theta_omega) | S,n]
- E[L(q_B, theta_omega) | S,n]
= (q_F - q_B)^2 &gt;= 0
</code></pre></div><p data-pid="cNAA5VDH">这说明：</p><p data-pid="SzQ3hVMK">在 posterior squared risk 意义下，Bayesian posterior mean <code>q_B</code> 不劣于 frequentist estimate <code>q_F</code>。</p><p data-pid="QB5rpPCi">如果 <code>q_F = q_B</code>，两者一样；如果 <code>q_F != q_B</code>，Bayesian 的 posterior expected loss 更低。</p><p data-pid="wpMBjtIm">完整证明可以看论文里的理论分析部分。这里保留最关键的结论：</p><p data-pid="VhMB3QFk">在小样本 skill evolving 里，如果我们用 posterior risk 来衡量估计质量，那么 Bayesian posterior mean 至少不比经验频率差。</p><h3>2.3 这对 skill rewrite 意味着什么？</h3><p data-pid="tlsHBecG">Agent skill evolving 里，我们最怕的不是“不改”。</p><p data-pid="uFCylwD6">更怕的是“乱改”。</p><p data-pid="UHYYRkjt">如果一次失败就 rewrite skill，很容易过拟合某个 case。</p><p data-pid="qjU9TDQO">如果永远不改，又无法从错误中学习。</p><p data-pid="FfFtf4hD">Bayesian 给了一个中间路径：</p><div class="highlight"><pre><code class="language-text"><span></span>rewrite if expected_gain - expected_cost - uncertainty_penalty &gt; 0
</code></pre></div><p data-pid="tNdMlJQM">也就是：</p><div class="highlight"><pre><code class="language-text"><span></span>Decision = E[Delta success | evidence]
           - lambda * token_cost
           - rho * uncertainty
</code></pre></div><p data-pid="J7-zJJkM">这不是为了把工程说得复杂，而是表达一个很朴素的原则：</p><ul>
<li data-pid="_9oIrUHa">一次失败不一定值得改；</li>
<li data-pid="JtjCFqLk">重复出现的失败才更值得改；</li>
<li data-pid="Gl5ZWnf7">高置信度的 failure mode 更值得写进 skill；</li>
<li data-pid="WHYT5FOg">低置信度的偶然失败应该先记录，不要马上污染 skill。</li>
</ul><p data-pid="5Z4M6GY5">这就是理论层面的第二个保证：</p><p data-pid="3WoTVztd">Bayesian update 能把先验、证据、不确定性和改写成本放到同一个决策框架里。</p><h3>2.4 failure mode 也可以 Bayesian 化</h3><p data-pid="TeauVY1J">真实 agent 失败不是只有 success / fail。</p><p data-pid="ZBJ1fRI2">失败也分类型：</p><ul>
<li data-pid="YrZaYy5K">missing output file；</li>
<li data-pid="tBqvJWrb">blank field crash；</li>
<li data-pid="Lx1F3JHS">invalid output format；</li>
<li data-pid="pdIVE2xN">wrong indicator calculation；</li>
<li data-pid="5ehkPu0_">missing verifier predicate。</li>
</ul><p data-pid="vUOYTtrY">这时可以用 categorical / Dirichlet belief：</p><div class="highlight"><pre><code class="language-text"><span></span>theta ~ Dirichlet(alpha_1, alpha_2, ..., alpha_K)
</code></pre></div><p data-pid="M-vV5dmb">如果第 <code>k</code> 类 failure mode 出现了 <code>c_k</code> 次，则：</p><div class="highlight"><pre><code class="language-text"><span></span>P(failure_mode = k | evidence)
= (alpha_k + c_k) / sum_j(alpha_j + c_j)
</code></pre></div><p data-pid="bBjKzBy_">这有什么用？</p><p data-pid="nOl1fjdm">它让系统知道：某个 failure mode 是不是已经从“偶然现象”变成“稳定模式”。</p><p data-pid="j2RUCqlm">只有当一个 failure mode 的 posterior 足够高，或者重复出现次数超过阈值时，才触发 skill patch。</p><p data-pid="FeOjbWhL">这就是我们说的“不是情绪化进化，而是证据驱动进化”。</p><h2>三、所以我们是双重保证</h2><p data-pid="rBeQ3XHX">第一重保证：实验上成立。</p><p data-pid="orgxEjYh">RealFin-Bench 里，Bayesian 在多个设置下明显超过 frequentist：</p><ul>
<li data-pid="74O7V-Ay">GA + pro：26/40 vs 23/40；</li>
<li data-pid="nt3NXPhl">BA native + flash：28/40 vs 15/40；</li>
<li data-pid="ngOIkiV8">BA native + pro：28/40 vs 18/40；</li>
<li data-pid="SrHnBj_s">GA + flash 打平，但 Bayesian token 更少。</li>
</ul><p data-pid="GeMB2izX">第二重保证：理论上合理。</p><p data-pid="R_Wqazx-">在小样本下，frequentist 的 <code>S / n</code> 方差大，容易极端；</p><p data-pid="Kld_X8eZ">Bayesian posterior mean 有 prior smoothing，有 uncertainty，有 failure-mode belief，可以更稳地决定：</p><ul>
<li data-pid="5ewVp3WI">什么时候信一个 skill；</li>
<li data-pid="wFXBod3V">什么时候改一个 skill；</li>
<li data-pid="aua1_kYi">什么时候只记录失败，不立刻改；</li>
<li data-pid="Stw5EkY0">什么时候把重复 failure mode 写成 patch。</li>
</ul><h3>最后总结</h3><p data-pid="ol-_rszK">如果任务很便宜、样本很多、失败成本低，直接按频率进化当然可以。</p><p data-pid="nPx3G39t">但 agent 任务往往不是这样。</p><p data-pid="l8ZzzaVn">真实 agent 每跑一个 case 都很贵：</p><p data-pid="Dnw8gzdm">tokens 贵，latency 高，benchmark case 少，真实业务失败更少。</p><p data-pid="S3y-zd8v">这时 skill evolving 最需要的不是“改得快”，而是“改得稳”。</p><p data-pid="Sk5ACamh">Bayesian-Agent 的核心价值就在这里：</p><p data-pid="VwNEpYo3">它把 agent 的每一次成功、失败、空文件、格式错误、指标漏算，都变成 belief update 的 evidence。</p><p data-pid="2vgD334f">然后再用 posterior belief 指导 skill rewrite。</p><p data-pid="BXP3xE6K">所以这不是“贝叶斯包装”。</p><p data-pid="zHlmAw0L">这是一个很实际的工程判断：</p><p data-pid="ozH_MzDp">当你不能等大样本统计稳定，又不能让一次失败污染整个 skill，Bayesian 是更适合 Agent skill evolving 的学习方式</p>
